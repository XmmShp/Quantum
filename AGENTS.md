# Official plugin development

- A feature that Quantum, another plugin, or an AI tool should discover or invoke must be exposed through NOF RPC. A Razor page, public C# method, or DI registration alone does not expose an RPC API.
- Define an `IRpcService` contract with `[TransportOverQuantum]`, stable `[RpcInvocationName]` names, one JSON-serializable request DTO per method, and `Result` / `Result<T>` return types. Add descriptions to services, methods, and request properties for catalog/schema consumers.
- Keep NOF source generators enabled in plugin projects. Declare `partial class ... : RpcServer<I...>` and let NOF generated assembly initializers register handler implementations. Do not duplicate these registrations.
- Test discovery through `quantum.rpc.catalog` and invocation by fully qualified RPC name through the host JSON boundary. Test actual reads/writes, validation, missing records, and cancellation; direct application-service tests alone are insufficient.
- Use RPC handlers as application use cases: put orchestration and repository/DbContext access in handlers, keeping domain invariants in domain objects. Do not add parallel ApplicationService/Session forwarding layers.
- Plugin pages must constructor-inject generated `I…RpcServiceClient` interfaces, registered with generated `Local…RpcServiceClient` implementations through the shared local RPC bootstrap. Handle failed Results before reporting success. Cross-plugin calls use the host `IRpcInvoker`.
- Keep stateful infrastructure (processes, connections, streaming state) in runtime adapters when required; pages may subscribe to change signals but must read and mutate business state through RPC clients.
- Throw NOF DomainException for business failures; Quantum supplies the NOF inbound pipeline and string enum JSON defaults. Do not add per-plugin RPC exception wrappers or enum converters.
- Test both generated local clients and host JSON dispatch, including request-scope isolation and recovery after failures. Keep NOF generators and native dispatch pipelines enabled.
- Read [docs/plugin-development.md](docs/plugin-development.md) before adding a plugin or public capability; update the plugin's RPC documentation and version when changing its published API.
- On this Windows development machine, every command invoking `dotnet` must run in a Windows administrator process.

# Code organization and style

- Keep one production type per file by default. Put each plugin's RPC interfaces in `Contract`, request DTOs in `Contract/Requests`, and public DTOs/enums in `Contract/Models`. Put server implementations and handlers in `Application` / `Application/Handlers`; keep a request and its dedicated response together when that improves navigation. Preserve existing RPC names and JSON contracts when reorganizing files.
- Use primary constructors for RPC handlers. Other services may use ordinary constructors with private readonly fields. Do not use positional records for transport data. Data records and Contract DTOs have no explicit constructors: declare get/set properties, mark mandatory members required, keep defaults on optional properties, and construct them using member initializers. Preserve property descriptions and JSON field behavior. Pinned `tests/Quantum.LedgerPlugin.Tests/HostRpc` source snapshots retain their upstream syntax.
- Use NOF expression mappings for entity-to-DTO conversion: declare simple pairs with [Mappable], register deliberate custom expressions with AddMapping, and place ProjectTo before materialization and after filtering/ordering/paging. Use the same mapping through IMapper for already materialized entities. Keep provider-specific enrichment outside SQL projection and verify translation with SQLite tests.
- Contract files contain transport definitions only; keep domain-to-DTO mapping in application code. Retain published CLR namespaces as well as RPC names and JSON contracts when moving existing types.
- Keep plugin initialization, database model configuration, and runtime adapters directly in each plugin root; do not introduce Hosting or Infrastructure folders for these files.
- Put pages and their component models in UI/Pages, and resource markers and resx files in UI/Localization. Use NOF services.AddRpcServer<T>() directly for RPC server registration; do not duplicate framework registration in Quantum.Sdk. Invoke cross-plugin canonical capability names directly through IRpcInvoker; query the catalog only for individual UI capability availability and do not require capabilities to share a provider. Do not recreate a Shared source directory or link SDK sources into plugin assemblies. Keep component namespaces and manifest component names aligned when moving UI code.
- Application, Domain, Infrastructure, and Contract must not use localization services or UI resources. Built-in business errors, status messages, and RPC catalog descriptions are English and culture-independent; localize them only at the UI boundary. Preserve user-authored text and external diagnostic content.
- Keep Razor markup in `.razor` and substantial component behavior in a matching `.razor.cs` partial. Retain small expressions inline; inline thin one-off wrappers instead of creating extra helper types. Keep shared rules/helpers only when they provide useful reuse.
- Follow `.editorconfig`: LF, UTF-8, four-space C# indentation, file-scoped namespaces, and braces for all control flow. Put block braces on separate lines and expand compact try/catch/finally blocks.
- Verify affected solutions in order: `dotnet restore`, `dotnet format`, `dotnet build`, `dotnet test`. Exclude pinned `tests/Quantum.LedgerPlugin.Tests/HostRpc` snapshots from formatting to preserve provenance hashes.
- Commit durable documentation: development guides, public API references, and required test provenance. Keep dated task audits, work logs, temporary verification reports, and local workspace references out of repository documentation.
